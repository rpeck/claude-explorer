## 1. How to use this report

- **This report is the spec for the testing session.** The testing session writes each test from this report and the plan. It never reads the code (plan §12.1).
- **Prerequisite: the frozen contract package (plan §12.2, task T4).** It holds the callable signatures, the request and response schemas, fixture manifests with exact expected values, the active-branch, cursor, and oversized-batch rules, the cache setup and invalidation controls, the instrumentation interfaces, and a map from each task to its tests. The coding and testing sessions get the same package. A contract change updates the spec before either role builds it.
- **Each test names a public surface.** The surfaces are:
  - an HTTP route, a script output, or a rendered page;
  - a file on disk or a cache file;
  - a public function that the plan names (`build_graph`, the steps extractor, the notification parser).
- **Each test has a pass condition and, where it matters, a "must not" condition.** A stub or a rubber-stamp implementation must fail the test (TESTING.md §5.3).
- **Each test lists its sources.** `O` is Opus, `G` is GPT, and `Gm` is Gemini. The source IDs let a reviewer check that the merge lost nothing.
- **Every end-to-end test asserts zero unexpected console errors and warnings** (TESTING.md §5.15). The tables do not repeat this rule.
- **For Radix controls,** click the control, then wait for a DOM or network signal. Do not use `.check()` (TESTING.md §3, "Radix `<RadioGroup>` `.check()` races"). The rule is written for RadioGroup. Apply it to Switch too, as a precaution.

## 2. How the lists were combined

1. **Same behavior, same test.** When two or three members proposed the same behavior, the test keeps the strongest pass condition and every "must not" condition.
2. **Same fixture, one parametrized test.** Behaviors that differ only in their input data became one table-driven test. Example: the five old result shapes and the `Task` tool name are one test (B1).
3. **Same user journey, one end-to-end test.** Playwright tests are slow, so behaviors on one page and one fixture became one journey with several checkpoints. Example: H7 covers six focus behaviors.
4. **Performance and compatibility tests are separate suites.** They do not run in the default suite. They run on a pinned commit with nothing else running.

## 6. What the combine step found

### 6.1 Problems in the plan (the plan is now corrected)

1. **`../` gave two answers.** The plan said that `../` gives 404, but the ID check rejects `.` and `/` with 422.
   - Now: an invalid ID that reaches the endpoint's ID check gives 422. A request whose decoded path does not match the route gives 404. Each traversal case names its exact request target and asserts a rejection and no file access.
   - Test D3 checks both.
2. **"The frontend request timeout" does not exist.** Decision S5 tied the first list call to it. The frontend sets no timeout on `/api/conversations` (verified in `frontend/src/lib/api.ts`). Now: T0 records a number, and test P3 uses it.

### 6.2 Proposals that the combine step did not take

- **Gemini's numeric budgets.** Examples: "under 500 ms" for parent detail, "under 300 ms" for the Graph layout, and "under 3.0 s" for the first list call.
  - The plan gives no such numbers, and nothing measured them.
  - The budgets come from T0 and T16. GPT marked the same budgets as not verified.
- **Gemini's limit of 50 step nodes in the whole Graph.** The plan's limit is 50 for each page and 200 in the Graph (S16). The tests use the plan's limits.
- **Gemini's API path `/api/conversations/<uuid>/agents/<id>`.** The API path is `/api/conversations/{uuid}/subagents/{agent_id}`. `/conversations/<uuid>/agents/<id>` is the page route.
- **Gemini's full journey test (E2E-01).** H3, H4, and H7 cover each of its steps already. One more long journey would only add run time.

### 6.3 Behaviors most likely to be missed

All three members named their top five. These behaviors had two or more votes, or point to a defect that a normal test suite does not find:

1. **An old result without a linked transcript keeps its data** (B2). Vote: GPT. An implementer can easily mix "pair a result with its call" and "link a call to a transcript".
2. **A meta-only change must update the graph and the enriched detail** (C2, C3). Votes: Opus, GPT. A cache that watches only the session file passes the simple tests.
3. **Batches must not split across pages** (F4, G5). Votes: Opus, Gemini. A split makes parallel calls look sequential. A layout that uses "recorded order" as a dependency makes a tall, wrong graph.
4. **`is_error: null` is not `false`** (F1, G7). Vote: Gemini. Code that converts the value to a boolean shows a success mark where no success was reported.
5. **The agent ID in every cache key** (C6). Vote: GPT. Message UUIDs can repeat between transcripts.
6. **A session with only internal runs keeps its way in** (G3, H5). Vote: Opus.
7. **Exiting focus restores the zoom, pan, and selection** (H7). Vote: Gemini.
8. **`elapsed_ms` is not `totalDurationMs`** (F2). Vote: GPT.
9. **The real downgrade round trip** (K1). Vote: GPT.
10. **No request for each agent when the user turns on Tool calls** (H9). Vote: Opus.
