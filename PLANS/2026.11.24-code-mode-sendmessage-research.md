## 1.2 Answers

### "Two scripts run at once in the same agent": your parallel reviewers are not this case

- **The key:** the link window is per **`session_id` + `agent_id`**. Only scripts that share both values can be confused.
- **Your parallel review subagents each have their own `agent_id`.** Verified:
  - **Hook input:** the hooks docs say that when a subagent calls a tool, `PreToolUse` and `PostToolUse` fire "and the input carries the `agent_id` and `agent_type`". The 2.1.330 binary builds hook input with `agent_id: g?.agentId` (function `Ym`).
  - **Transcripts on this Mac:**
    - Each subagent has its own file (`<session>/subagents/agent-<id>.jsonl`).
    - In 400 of 400 sampled files, the records carry `agentId` equal to the file's id, and 591 of 600 carry the parent's `sessionId`.
    - Main-conversation records carry no `agentId`. The 203 hits were legacy top-level `agent-*.jsonl` files, which do carry `agentId`.
  - The Code Mode docs also treat a subagent's script as its own ("From the main conversation, you don't see a subagent's code").
- **Separate peer sessions each have their own `session_id`,** so they never share a window either.
- **The one case left:** one agent (the main conversation, or one subagent) runs two Code Mode scripts at the same time.
  - This needs a **background script**: a script that keeps running while Claude goes on talking. That exists only in auto or bypass mode (next answer).
  - The changelog shows it happens ("once Claude started a second script that auto mode also allowed").
  - How often: only while a background script is still running when the same agent starts another script. The step 0 fixture records one such overlap so we can see it.
- **How the UI shows it:**
  - A call in the overlap is not linked.
  - It stays where it is, as a normal tool call, with a small label "made by a Code Mode script (one of 2 running)".
  - Both runs list it under "calls that may belong to this run".

### "Background scripts": not background agent sessions

- **"Background script"** means a Code Mode script (one `REPL` call) that keeps running inside one agent while Claude goes on with the conversation.
  - The Code Mode docs, "Long-running code": "Background: you can keep talking to Claude, and the code can run for up to two hours". This needs auto or bypass mode.
  - The binary has a `replToolUseId` field on the poll events that deliver a background script's result later.
- **It is not a background session:**
  - Background sessions (`claude --bg`, agent view) are whole sessions without a terminal.
  - The Code Mode docs list "you can't ... turn it into a background session" as a Code Mode limit.
  - A background session has its own `session_id`, so it never shares a window with another session.

### Background monitoring scripts (for example a watch for a PR review)

- **They are not Code Mode scripts.** A Monitor watch or a Bash command with `run_in_background` is one ordinary tool call. Its later events arrive as task notifications.
- **They do not affect Code Mode links.** They make no inner tool calls, so they never open a Code Mode window, and they never make a link ambiguous.
- **Explorer already shows them:** the call as a tool call, and each notification as a folded "Task notification" row (#52).
- **A Code Mode script that you run in the background** to watch something is a Code Mode run like any other. It counts toward the overlap rule only while it runs at the same time as another script in the same agent.

### Can Explorer tell which sessions have not exited? Mostly yes

- **Claude Code writes a `cost-state` record when a session exits.**
  - The binary marks its write policy as `"cost-state":"ends"`.
  - Its keys: `totalCostUSD`, `totalDuration`, `modelUsage`, `startTime`, and the like.
  - It appears from CC 2.1.257 on.
- **On this Mac**, for transcripts written by CC 2.1.280 or later:

  | Sessions | `cost-state` after the last turn | Without it |
  |---|---|---|
  | Not running now (not in the live registry) | 1,254 | 28 |
  | Running now (in `~/.claude/sessions/*.json`, pid alive) | 0 | 35 |

  - The 28 without it end mid-work (an assistant reply, then system records). They were killed, crashed, or their terminal was closed.
- **A resumed session** appends after its old `cost-state`, so "a `cost-state` after the last turn" is the right test, not "a `cost-state` anywhere".
- **Other end signals:**
  - a `continued-in` record (`continuedInSessionId`, 3 on this Mac): the session continued in another file;
  - the `SessionEnd` hook (`reason`: `clear`, `resume`, `logout`, `prompt_input_exit`, ...), which the opt-in hook can log.
- **Older transcripts (before 2.1.257)** have no end record. On this Mac that is about 4,000 files, mostly 2.0.x and early 2.1.x. Only time can tell for those.
- **Codex** writes `TurnStarted`, `TurnComplete`, and `TurnAborted` to the rollout, but not `ShutdownComplete` (`codex-rs/rollout/src/policy.rs`). It shows whether a turn is running, not whether the session exited.
- **The new rule for "active"** (it replaces the 15-minute default; §2.2.7):
  - **Running:** the session is in the live registry with a live pid (local machine only).
  - **Open:** no end record after the last turn, and the last record is less than 7 days old.
  - **Ended:** an end record after the last turn, or `continued-in`.
  - **Ended (no exit record):** no end record, and more than 7 days old. This covers crashes and old versions.
  - The "Active" filter means Running or Open.

### Launchers and meta-harnesses

- Every launcher surveyed leaves the same transcript in `~/.claude/projects` (or `~/.codex` for Codex). Explorer needs no launcher-specific code to read them (§2.5).
- **What differs is a little metadata Explorer can show:**
  - CC `entrypoint`: on this Mac, `sdk-cli` 2,421, `claude-desktop` 990, `cli` 223. The binary also knows `claude-vscode`, `sdk-ts`, `sdk-py`, `claude-code-github-action`, `remote`, `local-agent`, and `cowork`.
  - The session name (`agent-name`, `custom-title`).
  - A Remote Control id (`bridge-session`).
  - A PR link (`pr-link`).
  - Codex `session_meta.originator` and `source` (`cli`, `vscode`, `exec`, `mcp`, `subagent`).
- claude-code-ide.el, Herdr, tmux, and JetBrains run the CLI in a terminal, so they show as `cli`.

## 2.1 Topic A: Code Mode

### 2.1.1 What it is

- **Claude Code:** Claude writes JavaScript, and Claude Code runs it.
  - **Status:** experimental, off by default.
  - **Versions:** 2.1.323 added it (2026-11-12); 2.1.326 added agent teams; 2.1.331 added cloud providers.
  - **Turn on:** `CLAUDE_CODE_EXPERIMENTAL_CODE_MODE=1`.
  - **Limits:** interactive terminal only. Models: Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.2.
  - **Script API:** `` $`cmd` ``, `edit()`, `write()`, `tools`.
  - **Background scripts** (auto or bypass mode) run up to two hours while Claude goes on.
- **API:** programmatic tool calling. Each inner `tool_use` carries `caller.tool_id`.
- **Codex:** the freeform tool `exec` and the `wait` tool. Feature `code_mode`, `UnderDevelopment`, off by default.

### 2.1.2 How Claude Code records a run

**Certain:**

- **Outer call:** a `tool_use` named `REPL`, with `input.code`.
- **Result (`toolUseResult`):** `code`, `result`, `stdout`, `stderr`, `toolsUsed`, plus optional `error`, `images`, `documents`, `imagePagesFailed`, `refusedCalls`, `uncutOutputNote`.
- **Inner call ids** start with `repl_` or `toolu_cc_`.

**Binary, not verified:**

- `Eval` is an alias; the UI label is `Code`.
- Inner calls are `isVirtual` records. `progress` records have `data.type: "repl_tool_call"`.
- Background results come back as poll events with `replToolUseId`.
- Candidate parent fields: `replToolUseId`, `script.toolUseID`.

```json
{"type":"assistant","message":{"content":[{"type":"tool_use","id":"toolu_01OUTER","name":"REPL","input":{"code":"const f = await $`rg -l TODO src`.text();\n({ files: f.trim().split('\\n') })"}}]}}
{"type":"assistant","isVirtual":true,"message":{"content":[{"type":"tool_use","id":"toolu_cc_0a1b2c","name":"Bash","input":{"command":"rg -l TODO src"}}]}}
{"type":"user","isVirtual":true,"message":{"content":[{"type":"tool_result","tool_use_id":"toolu_cc_0a1b2c","content":"src/app.py\n"}]}}
{"type":"user","message":{"content":[{"type":"tool_result","tool_use_id":"toolu_01OUTER","content":"{\"files\":[\"src/app.py\"]}"}]},"toolUseResult":{"code":"...","result":"{\"files\":[\"src/app.py\"]}","stdout":"","stderr":"","toolsUsed":["Bash"]}}
```

### 2.1.3 How Codex records a run

- **`exec`:** a `custom_tool_call` with `input` = the JavaScript.
- **Outputs:** `custom_tool_call_output` records with the same `call_id`. Each begins with a header: `Script completed`, `Script failed`, `Script terminated`, or `Script running with cell ID <id>`, then `Wall time`, then `Output:`.
- **More outputs:** `notify()` adds outputs to the same `call_id`. `wait` (with `cell_id`) continues a yielded cell.
- **Nested tools:** `exec-<uuid>`, with no parent field.
- **Explorer today (#87):** shows the outer call and its output; nested items show as separate messages.

### 2.1.4 Linking inner calls to their script

**Hooks fire for scripts and inner calls, but carry no parent id:**

- **Hook input fields** (docs and binary `Ym`, `P_e`): `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`, `agent_id`, `agent_type`, `tool_name`, `tool_input`, `tool_use_id`, `mcp_server`, and after the call `tool_response` and `duration_ms`.
- **OpenTelemetry** cannot tell which script made a call (Code Mode docs).
- **Auto mode refuses a script that a hook changed** (binary), so a hook cannot tag the calls.
- **Codex hooks** have no cell field.

**The exclusive-window rule:**

- An inner call runs only while its script runs.
- Within one `session_id` + `agent_id`: if exactly one script is open, the link is exact. If two or more are open (background scripts only), the call is `ambiguous` and is not linked.
- Parallel subagents and peer sessions never share a window (§1.2).

**Sources, in order:**

1. A parent field in the transcript, if step 0 finds one. It works for every session.
2. Otherwise the opt-in hook log, for new sessions on machines that have the hook.
3. For Codex, the rollout's alive cells: from the `exec` call to a final status, including `wait` outputs.

Sessions with no source keep their calls marked `from_code_mode` (by id prefix), with no link.

### 2.1.5 The opt-in hook (only if the transcript has no parent field)

- **Install:**
  - `claude-explorer install-cc-hook [--uninstall]` and a Settings button. Both show the exact JSON to be added to `~/.claude/settings.json` and ask for consent.
  - A backup is written first. Only user settings are changed.
  - The entries are marked, so uninstall removes only them.
- **Entries:**
  - `PreToolUse` on `REPL`: synchronous, 2 s, `onFailure: "continue"`.
  - `PostToolUse` and `PostToolUseFailure` on `REPL`: synchronous, 2 s.
  - `PreToolUse` on `*`: `async`. It exits at once unless the id starts with `repl_` or `toolu_cc_`.
  - `SessionEnd`: `async`. It logs the `reason`, which helps the "active" rule.
- **The program** `~/.claude-explorer/cc-hook.py`:
  - It prints nothing. Async hook output reaches Claude's context.
  - It appends id-only lines to `~/.claude-explorer/cc-code-mode/<session_id>.jsonl`, rotated at 10 MB:

    ```json
    {"v":1,"ev":"pre","session_id":"aaaaaaaa-0000-4000-8000-000000000001","agent_id":null,"tool_use_id":"toolu_cc_0a1b2c","tool_name":"Bash","t_ns":1764000000123456789,"pid":4242}
    ```

- **The join:** sort by `t_ns`; apply the exclusive-window rule per `session_id` + `agent_id`; a missing `post` closes the script at the session's last record.
- **Sessions before the hook, and machines without it:** no per-script link. Bundles and the sync folder carry `cc-code-mode/` (issue 3).
- **Overhead:**
  - one process start per tool call (async, not blocking Claude);
  - two short synchronous hooks per script;
  - a `PreToolUse` hook that matches Bash turns off CC's "shell head start" for Bash (binary reason `hook`).
  - Step 0 measures this, and the consent dialog states it.
- **Failure modes:**
  - the hook fails or times out: the call still runs, and the gap makes calls `ambiguous`;
  - a corrupt line is skipped;
  - the disk is full: lines are lost.
- **Privacy:** ids, tool names, times, and pids only.

### 2.1.6 Data model

- **`ContentBlock.code_run`** with `inner_calls[]`. Each call has `link_source`: `transcript_field`, `hook_log`, `exclusive_window` (Codex), or `caller_field` (API).
- **`code_run_parent`** on linked calls.
- **`from_code_mode`** on unlinked calls, plus `ambiguous_with: [run ids]` when two runs were open.
- **Codex:** `CODEX_PROJECTION_VERSION` 5.

## 2.2 Topic B: SendMessage and cross-session messages

### 2.2.1 What it is

- **Tools:** `SendMessage` and `ListAgents`.
- **Versions:** 2.1.224 (local), 2.1.225 (Remote Control on other machines), 2.1.234 (Windows), 2.1.236 (`notify_when_idle`), 2.1.248 (cloud providers).
- **Transport:**
  - local sessions over a per-session socket;
  - other machines and cloud sessions through Anthropic, while connected to Remote Control.

### 2.2.2 Records

- **Sender:**
  - input: `to`, `message`, `summary`, `type`, `recipient`, `content`, and optional `notify_when_idle`;
  - cross-session result: `{success, message, display, msg_id}`;
  - subagent result: `{success, message, pin, resumedAgentId?}`.
- **Receiver, new turn:** a `user` record with `isMeta: true`, `turnOrigin: "peer"`, and `origin` = `{kind: "peer", from, fromMode, name, msg_id, verifiedPeerPid, hopChain?, body}`.
- **Receiver, mid-turn:** an `attachment` with `type: "queued_command"`, `prompt`, and `origin`.
- **Hand-back:** `origin.handback: true` and `senderTaskId`.
- **Idle notice:** an `isMeta` user record with no `origin`, text `[Cross-session idle notice] "<name>" ...`.
- **Remote Control id:** a `bridge-session` record (`bridgeSessionId`, a 3-letter prefix and 24 more characters; 29 sessions on this Mac, one id each). It maps a local session to its Remote Control id.
- **Newer senders (binary):** `origin.fromSession`.

### 2.2.3 What Explorer does today

- Mid-turn messages are dropped (141 of 376 on this Mac).
- Turn messages show the raw envelope.
- No links.
- Codex agent messages show as `agent_message` tool calls (#71), with no thread link.

### 2.2.5 Linking rule

1. Exact `msg_id`.
2. `fromSession`, or a Remote Control id that a `bridge-session` record maps to a session.
3. Subagent keys, with #46.
4. **Idle notice:** the one earlier `notify_when_idle` send in the same session with the same `to`.
5. **Codex:** agent path to thread within one tree (`session_meta.agent_path`, `parent_thread_id`). Then the sender's tool call by recipient and equal text; if several match, link at session level only.
6. Nothing by name, socket, or time alone.

### 2.2.6 What a received message shows

| Shown | Not shown |
|---|---|
| "Message from @name" (link) | Prefix line, tags, safety paragraph |
| The body, in full | Delivery path, `msg_id`, pid, socket (available in MCP output and the bundle export) |
| "Sent because of: <first line of the sender's prompt>" (link) | The raw text (only "Copy raw" in the "..." menu, if it needs no new API field) |
| A mode chip when not `prompting`, and "Relayed through N sessions" | |

### 2.2.7 Session state: Running, Open, Ended

| State | Rule | Source |
|---|---|---|
| Running | In `~/.claude/sessions/<pid>.json`, and the pid is alive. Also busy, idle, or waiting status. | Live registry, local machine only. Read in place; never copied. |
| Open | No end record after the last turn, and the last record is less than 7 days old | Transcript |
| Ended | A `cost-state` after the last turn, `continued-in`, or a logged `SessionEnd` | Transcript, hook log |
| Ended (no exit record) | No end record, and the last record is 7 days old or more | Transcript |

- **Codex:**
  - Open means a `TurnStarted` without a later `TurnComplete` or `TurnAborted`, or the last record is less than 7 days old.
  - There is no exit record, so Ended means older than 7 days.
  - A running Codex process is not detected in version 1.
- **The "Active" filter atom** means Running or Open.
- **Failure modes:**
  - **A crashed session** stays Open for 7 days.
  - **A session left open in a terminal for weeks** shows Ended (no exit record) on another machine, but Running on its own machine through the registry.
  - **Versions before 2.1.257** have no end record.
  - **The registry is a live format** that Claude Code can change. If it fails to parse, Explorer falls back to the transcript rule.
- **Why the registry now:** it is the only exact "running now" signal. All 35 entries on this Mac had live pids and matched a transcript. It is small, local, and read only.

## 2.3 How to draw data flow and messages

### 2.3.1 Facts

- **Messages on this Mac:** 74 sessions in groups of 66, 6, and 2; one session messaged 64 others; at most 17 messages per pair.
- **The work laptop** has orchestrators with sub-orchestrators.
- **Code Mode files** do not record which output fed which input.

### 2.3.2 Views

- **Messages tab:** a Sequence view (lanes = sessions, time down, a click opens the message), a Graph view (hierarchy, counts), and a List view.
- **Code Mode:** a Sequence view with lanes for the model, the script, and each tool.
- **Subagents:** the #46 Graph and Tree.
- **Components:** `SequenceDiagram.tsx` (plain SVG or CSS grid) and the #46 `@dagrejs/dagre` graph. No Mermaid.
- **Prototype first,** on fixtures, at 2, 8, 20, and 60 lanes.

### 2.3.3 Messages tab controls

**1. Default view: all active sessions.** The user's decision. The tab opens with every session that is Running or Open (§2.2.7) and the messages between them. "k hops" below is the other scope: it centers the view on one session.

**Scope: k hops**

- A number control, 1 to 5, plus "all" (the whole connected group). The scope can also follow #46 subagent edges (a toggle).
- **Default k = 2, with hop-2 sessions folded under the hop-1 session that reaches them.** The reasons:
  - **From a worker,** k = 1 shows only its orchestrator. k = 2 also shows the sibling workers, which is the usual question ("who else works on this").
  - **From an orchestrator,** k = 1 already shows dozens of peers, and k = 2 adds every worker of every sub-orchestrator. Folding keeps that readable: each sub-orchestrator shows as one row "+N sessions", which expands on a click.
  - **On this Mac,** the coordinator at k = 1 has 64 peers. With folding at k = 2, the lane count stays at 65 or fewer until you expand a group.
- k and the open folds persist per session.

**2. Filters:** the named filter graph (`filterEngine.ts`), with new atom targets:

- `message_text` and `ticket` (for example `#84`);
- `project`, `source`, `machine`, and `entrypoint`;
- `state` (Running, Open, Ended; §2.2.7). "Active" is a named filter `state in [Running, Open]`.

The Messages tab has its own active filter and a time-range picker.

**3. Hierarchy (derived, and labeled so):** a session's parent is the sender of its first message. Lanes go depth first, and edge width shows the count.

**4. Actions:**

- collapse and expand a subtree;
- pin;
- hide (with a "Hidden: N" chip);
- a lane limit (default 12) with an "N other sessions" lane and a picker.

**5. No exceptions:** a filter that hides the open session hides it, and the empty state says so.

## 2.4 Topic C: an archive across machines

### 2.4.1 What Explorer has now

- **One `data_dir`.**
- **Codex** is copied to `codex/<home_key>/`. `home_key` comes from the path, so it collides across machines with the same home path.
- **CC and local Cowork sessions are not copied** (the known gap).
- **`ArchiveLock`** works on one machine only.
- **The D13 cloud-sync consent gate** protects every write.

### 2.4.2 Design

- **Layout:** `<root>/machines/<machine-id>/{machine.json, manifest.json, claude-code/, codex/, cowork/, cc-code-mode/}`.
  - `<machine-id>` is a random UUID with a label; never the hostname.
  - One writer per folder.
  - Each machine builds its own search index; it is never shared.
- **Export rules per machine** (`export-rules.json`):

## Issue 4

**Title:** Ticket view: every session that worked on a GitHub issue, across machines and launchers

### Why it matters

When a ticket is filed on one of my repos, I start sessions on it in different ways: from Emacs with claude-code-ide.el, in the cloud, or from my work laptop. Later I want one place that shows what happened: which sessions worked on it, where, what they told each other, and which PR came out. Other users start sessions with other tools (Herdr, VS Code, Cursor, the Desktop app), so this must not depend on any one launcher.

### The ask

- Group sessions by GitHub issue, from data Explorer already has.
- A ticket page: the sessions (machine, launcher, state), the messages between them (issue 2's Messages tab scoped to the ticket), and PR links.
- An optional "start a session" command template, empty by default, that Explorer fills and copies. Explorer runs nothing.

### What the data looks like

- A title or message with `#84`, `owner/repo#84`, or an issue URL.
- The `gitBranch` field, for example `fix/84-search-tools`.
- Exact PR links:

  ```json
  {"type":"pr-link","sessionId":"aaaaaaaa-0000-4000-8000-000000000001","prNumber":85,"prRepository":"owner/repo","prUrl":"https://github.com/owner/repo/pull/85","timestamp":"..."}
  ```

  This Mac has 4,611 such records.
- The launcher from `entrypoint` (`cli`, `claude-desktop`, `claude-vscode`, `sdk-cli`, ...) and, for Codex, `originator` and `source`.

### Proposed design

1. **Extraction:** a `ticket_refs` table (repo, number, session, message, kind: title, message, branch, or pr-link), filled by the drift pass. A bare `#N` takes the repo from the session's git remote when it is known, else "unknown repo".
2. **Ticket page** `/tickets/<owner>/<repo>/<n>`: sessions with machine, `entrypoint` chip, state, and times; the Messages view scoped to them; PR links from `pr-link`. No GitHub API calls in version 1.
3. **A `ticket` filter target** for named filters (shared with issue 2).
4. **An optional start command** (`start_session_command`, empty by default):
   - placeholders `{repo}`, `{issue}`, `{title}`, `{cwd}`;
   - the docs show examples for `claude --cloud`, `claude --bg`, claude-code-ide.el through `emacsclient`, and Herdr;
   - Explorer fills the template and copies it to the clipboard. It runs nothing.
5. **MCP:** `list_sessions(ticket="owner/repo#n")`.

### Tests

- Synthetic sessions with each reference kind, including `pr-link`.
- A bare `#n` with and without a known remote; two repos with the same number.
- Sessions on two machines (issue 3) and with several `entrypoint` values, including an unknown one.
- The ticket page, the filter target, the MCP filter.
- The start template: empty by default (no button); filled placeholders; nothing is run.

## msg_id coverage (cross-session messages): `survey_sm6.py`

```python
# Shape-only: which peer records lack msg_id, by kind, version, month. Sender calls without msg_id, by target kind and result class.
import json,glob,os,re,collections
root=os.path.expanduser('~/.claude/projects')
files=glob.glob(root+'/**/*.jsonl',recursive=True)
C=collections.Counter
recv=C(); recv_ver=collections.defaultdict(C); recv_month=collections.defaultdict(C)
send=C(); send_ver=collections.defaultdict(C); send_month=collections.defaultdict(C)
other=C()
def to_kind(to):
    if not isinstance(to,str): return 'nonstr'
    if to.startswith('uds:'): return 'uds'
    if to.startswith('bridge:'): return 'bridge'
    if re.match(r'^(session_|cse_|ses_|local_)',to): return 'remote-id'
    if re.fullmatch(r'a[0-9a-f]{16}',to): return 'subagent-id'
    if to=='main': return 'main'
    return 'name'
def res_class(text,tur):
    t=(text or '')
    if isinstance(tur,dict) and 'resumedAgentId' in tur: return 'subagent resumed'
    if isinstance(tur,dict) and 'pin' in tur: return 'subagent queued'
    if "main conversation" in t: return 'to main'
    if t.startswith('Not sent') or 'NOT delivered' in t or 'Not delivered' in t: return 'not sent/delivered'
    if 'refused' in t.lower(): return 'refused'
    if 'Remote Control' in t or 'cloud' in t.lower(): return 'remote/cloud'
    if 'no agent named' in t.lower() or 'not found' in t.lower() or 'No session' in t: return 'unknown target'
    if isinstance(tur,str) or (isinstance(tur,dict) and tur.get('success') is False): return 'error'
    return 'other'
for f in files:
    try: lines=open(f,errors='replace').readlines()
    except: continue
    sm={}
    for l in lines:
        if not ('SendMessage' in l or 'peer' in l or 'cross-session' in l or 'agent-message' in l or 'idle' in l or sm): continue
        try: r=json.loads(l)
        except: continue
        ver=r.get('version') or '?'; month=(r.get('timestamp') or '?')[:7]
        cont=(r.get('message') or {}).get('content')
        if isinstance(cont,list):
            for b in cont:
                if not isinstance(b,dict): continue
                if b.get('type')=='tool_use' and b.get('name')=='SendMessage': sm[b['id']]=(b.get('input') or {})
                if b.get('type')=='tool_result' and b.get('tool_use_id') in sm:
                    inp=sm[b['tool_use_id']]; tur=r.get('toolUseResult')
                    has=isinstance(tur,dict) and bool(tur.get('msg_id'))
                    c=b.get('content'); 
                    if isinstance(c,list): c=' '.join(x.get('text','') for x in c if isinstance(x,dict))
                    try: text=json.loads(c).get('message','') if isinstance(c,str) and c.startswith('{') else c
                    except Exception: text=c
                    k=(to_kind(inp.get('to')), 'msg_id' if has else 'NO msg_id', 'with notify' if inp.get('notify_when_idle') else '', res_class(str(text),tur) if not has else '')
                    send[k]+=1
                    if not has and k[0] in ('name','uds','remote-id','bridge'): send_ver[k][ver]+=1; send_month[k][month]+=1
        o=None; kind=None
        if r.get('type')=='user' and isinstance(r.get('origin'),dict): o=r['origin']; kind='user turn'
        a=r.get('attachment')
        if r.get('type')=='attachment' and isinstance(a,dict) and isinstance(a.get('origin'),dict): o=a['origin']; kind='attachment:'+str(a.get('type'))
        if o is not None:
            ok=o.get('kind')
            if ok=='peer':
                sub='handback' if o.get('handback') else ('cross-session' if str(o.get('from','')).startswith('uds:') else ('from agent id' if re.fullmatch(r'a[0-9a-f]{16}',str(o.get('from',''))) else 'peer-other:'+re.sub(r'[0-9a-f]','h',str(o.get('from','')))[:12]))
                k=(kind,sub,'msg_id' if o.get('msg_id') else 'NO msg_id')
            else:

            recv[k]+=1

        # envelopes in user text without origin (older versions?)

            k=('user text, no origin','cross-session envelope'); recv[k]+=1; recv_ver[k][ver]+=1; recv_month[k][month]+=1
        if r.get('type')=='user' and not isinstance(r.get('origin'),dict) and isinstance(cont,str) and cont.lstrip().startswith('<agent-message'):
            k=('user text, no origin','agent-message envelope'); recv[k]+=1; recv_ver[k][ver]+=1; recv_month[k][month]+=1
        if r.get('type')=='system' and re.search(r'idle|cross-session|peer',json.dumps(r.get('subtype'))+str(r.get('content',''))[:200],re.I):
            other[('system',r.get('subtype'))]+=1
        if r.get('type')=='attachment' and isinstance(a,dict) and re.search(r'idle|peer|cross',str(a.get('type')),re.I):
            other[('attachment',a.get('type'))]+=1
def top(d,n=6): return ', '.join(f'{k}:{v}' for k,v in sorted(d.items(),key=lambda x:-x[1])[:n])
```
