### The 5 Behaviors Most Likely to be Missed by an Implementer

1. **Connector Semantics in the Graph View (Decision S10)**
   * *Why it will be missed:* When tool calls are enabled in the Graph, developers will naturally feed the sequential tool steps into `@dagrejs/dagre` as dependency edges. This will cause Dagre to compute strict hierarchical ranks for every tool call, resulting in an unnaturally tall, unreadable vertical graph that falsely implies Tool B depended on the output of Tool A. The requirement is that connectors mean *"recorded next"* (chronological order), while parallel tool calls sharing a `message.id` must sit side-by-side in the same rank. An implementer who treats the sequence as a standard DAG will create a broken, unreadable layout for sessions with many tools.

2. **Truthful Error Handling: `is_error: null` vs `false` and "No errors in inspected activity" (Decisions S12, S13)**
   * *Why it will be missed:* Standard frontend habits favor boolean coercion (`!!step.is_error`). If `is_error` is `null` (because the underlying tool-result row omitted the flag), coercing it to `false` causes the UI to render a green "success" checkmark where no success was actually reported. Furthermore, implementers frequently display unqualified UI copy like `"No errors"`, which is misleading when the app has only inspected a 50-step window of a 14,000-call session. The spec strictly demands `"no error reported"` for `null` and the exact notice `"No errors in inspected activity"`.

3. **Viewport &amp; State Restoration when Exiting Focus Mode (Decision S11)**
   * *Why it will be missed:* It is easy to write `setFocus(null)` and let React re-render the default graph. But when a user focuses on an agent, examines its subtree, and then hits "Exit Focus" (or uses the breadcrumb), they expect to return to the exact zoom level, pan position, selected node, and switch state they had before entering focus. Re-mounting the Graph or resetting pan/zoom to origin (0, 0) is extremely disorienting, especially in larger sessions.

4. **Preserving Raw Content on Notification Cards (Decisions R12, Step 1.3/1.4)**
   * *Why it will be missed:* When converting `&lt;task-notification&gt;` bubbles into rich "Subagent finished" cards, implementers often replace the raw message `content` string with the parsed JSON structure. Doing this silently breaks session Markdown/PDF export, text search, and clipboard copying, which still rely on `message.content`. Furthermore, implementers will likely forget the negative-space requirement: if a user legitimately typed `&lt;task-notification&gt;` in a regular prompt, it must *not* render as a Subagent Finished card unless `&lt;task-id&gt;` matches a verified agent ID in that session.

5. **Keyboard Traps and Radix Radio/Switch State Races (Decision R20, `playwright.md §3`)**
   * *Why it will be missed:* The Tree view requires full Vim (`j`/`k`), Emacs (`n`/`p`), and Arrow key support while integrating with the existing `focusArea` model. Implementers often bind global key listeners that accidentally intercept `j`/`k` or `Esc` while the user is typing in a search input, filter box, or open modal. On the testing side, Playwright tests that use `.check()` on Radix `Switch` or `RadioGroup` components will flake due to microtask state races against TanStack Query cache mutations (as documented in `playwright.md §3`). Implementers and testers must use explicit `.click()` actions followed by durable DOM/response assertions.
